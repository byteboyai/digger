## 1. 目标与交付边界

本轮保留现有分层，依次解决异常后的恢复、输入高频路径的全量工作，以及组合根和验证流程的维护成本。Markdown 文本继续由 Rust 持有权威版本，块 ID、作者与 Agent 的并发修改规则继续遵守 ADR-012 / ADR-013。

| 阶段 | 必须交付 | 独立完成条件 |
|---|---|---|
| R：恢复性 | 项目迁移可重入、块计数不溢出、同步拒绝可收敛、清理队列故障可见、编辑器创建可重试 | A1–A5 |
| P：性能 | 坐标与元数据扫描优化、增量块回包、后台 SQLite 用量账本、可重复的完整路径测量 | A6–A9 |
| E：工程质量 | 组合根按职责拆分、行为测试与 web 产物检查进入 CI、无 patch 验证 | A10–A12 |

阶段 R 可以先单独交付。整个优化项目只有完成 A1–A12 才可标记完成；阶段完成不得代替整体完成。

不在本轮新增章节持久化、生产 Agent 运行时、跨设备协作、通用插件协议或跨产品数据库。不因本轮优化扩大 normal 模式下页面的写权限。Rope、编辑器后台 actor 和新的共享平台抽象暂不列为必需交付；只有完整路径测量证明仍有明显瓶颈时，另写决策与任务。

## 4. 项目库迁移协议

### 4.1 数据提交与归档分离

由 Digger 在目标库维护命名隔离的迁移记录表，例如 `digger_migration_runs`。不得占用共享 store 的全局 `PRAGMA user_version` 或修改其表定义。记录至少包含迁移类型 / 格式版本、规范化来源身份、完成时刻和复制计数；用于诊断的来源摘要必须基于同一读取快照中的逻辑行，不能仅哈希 SQLite 主文件而忽略 WAL。

源行复制与完成标记在目标数据库的同一事务中提交。重启后：

1. 无标记且存在 legacy：验证、复制、写标记；真实目标冲突整体失败，不使用 `INSERT OR IGNORE` / `REPLACE` 掩盖冲突。
2. 有对应完成标记且存在 legacy：不再插入，只继续归档。
3. 有完成标记且 legacy 已归档或不存在：返回已完成。
4. 来源身份不符、无法验证或归档目标冲突：返回可诊断的冲突，不覆盖任何文件。

归档失败是“数据已迁移、归档待完成”，不能令已可用的项目服务退回不可用；通过结构化 outcome 和产品提示暴露。不得覆盖既有 `.migrated` 文件。新数据提交后，不以删目标库的方式回滚。

### 4.2 已发生旧版半完成迁移

旧版可能已经复制数据而没有新标记。恢复工具 / 路径必须在事务内按旧 schema 的规范化投影，逐行核对 projects、memories、memory_history 的原始身份和内容。全部来源行都与目标一致时，可以补写标记并进入归档；目标额外行不自动删除。任何来源行缺失或内容不同均停止自动恢复，给出冲突信息，不把部分碰巧相同当作迁移成功。

迁移使用数据库事务串行化，并在锁内重新检查标记。不能仅凭调用前 `target.exists()` 判断有权删除数据库及其 sidecar；失败清理只能处理本次调用明确拥有、且未成功提交的数据文件。现有真实冲突保护、旧 schema 支持和 ID 保留行为继续有效。

## 5. 块匹配计数与工作量

词频、片段频次及其统计计算统一使用可容纳输入长度的 `usize`，检查聚合和候选数量乘法。计数与相似度分母使用一致口径，不靠单独饱和一个字段改变分数。

重复 token、重复中文片段和大量同句输入在 Debug / Release 下都不能 panic 或回绕。保留现有候选配对预算；对长度相关的字符 diff 补充工作量约束。预算不足时保守分配新块 ID并记录降级诊断，不用低可信匹配复用其他块 ID。阈值由确定性语料测量后冻结，不在此预设未经测量的文档大小限制。

## 6. 编辑同步恢复与协议

### 6.1 请求身份和错误

编辑请求增加会话内单调 request ID；回包携带对应 ID、版本与结构化错误码。错误码至少区分 stale base、bad position、malformed changes、unauthorized、unsupported protocol、internal。`reason` 仅用于展示，不参与状态机分支。

新增 normal 模式可用的只读快照请求，受原 nonce / generation 约束。`Load` / harness Agent 操作仍只允许 SelfTest。握手声明协议版本，Rust 与编译进二进制的 web 产物同次更新；版本不匹配时停止编辑同步并提示，不能误读成旧格式继续发送。

同一会话只允许一个编辑请求在途。重复的最近已提交 request ID 返回原提交结果，不再次应用；同 ID 不同内容为协议错误。无法确认的旧 ID 不猜测成功，也不盲目重放。过时回包不能清空当前请求或改写版本。

### 6.2 恢复状态机

页面显式维护 `opening / ready / sending / recovering / conflict / failed / closed`，sent 和 queued 是有身份的未确认修改。保存最后确认基线与当前本地文本，直到收到对应确认。

- StaleBase：只有具备从确认基线到目标版本的完整变更链时，才转换并重试；否则请求快照，不无限重发旧 base。
- 非 stale 拒绝、超时或非法回包：保留草稿，停止发送新补丁，进入 recovering；不能只清 sent 后继续使用 queued 的旧坐标。
- 能证明可安全重放时恢复 ready。无法证明时进入 conflict，显示同步失败，保留可复制 / 导出的本地文本；用户明确选择后才采用 Rust 快照或将草稿作为新编辑提交。
- 快照返回及恢复期间的新输入必须有确定归属；可以暂时禁用继续输入，但必须保留已有草稿。不得以整篇覆盖解决并发 Agent 修改。
- `settled()` 只在全部请求确认后成功；failed / conflict / closed 应使等待者以类型化错误结束。超时必须有界且可测试，不能留下永久悬挂 Promise。

恢复缓冲属于当前内存会话，不宣称解决进程崩溃后的章节保存。未经明确处置，不得通过重建页面丢弃恢复中的草稿。

## 7. 增量回包与输入路径

### 7.1 扫描与缓存

对一批有序修改，单次遍历转换 UTF-16 端点。缓存文档长度与必要的字符统计，根据删除 / 插入片段更新。块范围使用有序边界顺序计算，移除不必要的排序和边界 HashMap。缓存以 version 为边界，失败编辑、Agent 回滚、load / restore 都必须保持一致。

普通编辑确认不要求重新计算全文 FNV。全文 hash 保留在首次打开、恢复快照和显式一致性检查中，避免把原 FNV 冒充可局部更新的哈希。现有 harness 的最终 hash 验证继续执行。

### 7.2 线上块增量

协议提供两种明确的块结果：完整快照与增量。增量携带 baseVersion、resultVersion、被替换的旧块连续区间、结果版本坐标下的新块，以及映射未替换块所需的文本 changes。旧区间索引属于 baseVersion 的已确认块集合；先映射保留块，再替换指定区间。之后才把 sent / queued 叠加到前端展示范围上，防止重复映射。

一次修改可能需要扩大替换区间，或回退完整快照；大范围改写、重排和无法证明等价的情况允许回退。增量必须覆盖删除块、块类型 / 标题变化和边界邻居变化；诊断字段 `how` 按本次提交解释：保留块为 `Exact`，替换区间使用新回包值；完整与增量逐字段对照测试。请求身份、版本不连续或应用结果不合法时进入恢复，不继续拼接。

首次打开、显式恢复和检查点允许全文工作；普通局部输入不能无条件走完整块回包。前端局部范围映射仍可能与块数相关，本轮不宣称端到端 O(1)。

### 7.3 性能验收

新增可重复基准，至少覆盖 100 / 1000 / 5000 块，中英文、emoji、开头 / 中间 / 末尾输入、多端点替换、大粘贴与 Agent 并发。基准分开报告 Doc、Bridge + 序列化、前端应用、真实 webview 往返，记录回包字节数、p50 / p95、解析字节数和完整回退次数。

同机器同 Release 配置进行前后对比，记录预热、样本数与机器信息。对触及不超过 8 个块的 5000 块语料，常规确认回包应比基线减少至少 90% 字节，Rust 处理与序列化的 p95 至少改善 2 倍；100 块场景不得稳定回退超过 10%。真实 webview 结果单列，不以纯库耗时代替。普通 CI 以确定性正确性、回包大小和工作计数为门禁，耗时门槛放在固定环境基准。

## 8. 用量账本后台事务化

### 8.1 存储与并发

新增产品路径 `usage_db_path()`，指向 Digger 自己的 `state/usage.sqlite3`；旧 `config/usage_ledger.json` 路径保留为导入源。独立库避免改动 daemon 与共享项目 store 的 schema。数据根覆盖规则和 Dozer 隔离保持不变。

单个后台存储工作线程拥有 SQLite 连接，接收有界命令并返回持久化确认。窗口 update 只提交命令、处理结果，不等待磁盘。查询同样走后台接口，不在 Tokio worker 上直接长时间执行同步 SQLite。

新库显式配置 WAL、有限 busy timeout 和提交同步策略；以 `synchronous=FULL` 作为已确认记录的持久化配置。锁等待与重试都有上限，不能让退出排空无限等待。正常关闭连接和 checkpoint 属于工作线程职责，不搬回窗口线程。

表以 run_id 为唯一键；索引至少覆盖 `(project_path, finished_ts_ms, run_id)`。完整 DTO 可保存在带版本的 payload 中，保留全部 token / 文件 / agent 字段；索引字段与 payload 在同一事务中更新。SQLite 的有符号整数范围须显式校验，不允许 `u64 as i64` 静默截断。相同 run_id 继续执行累计值 upsert，项目过滤和时间单位不变。

### 8.2 写入结果与退出

生产者区分 pending、persisted、failed。只有事务提交后才能报告已记录；失败向界面传播并保留可重试的原完成事件，不因提前从 RunningTasks 取走而丢失重试上下文。查询仅把已提交事实当成账本结果，不能返回未落盘内存行冒充成功。

有界队列满时产生明确可重试结果，不能丢事件或阻塞窗口。重试必须用同一 run_id 与同一完成事件，不重新计算结束时刻。正常退出停止新提交、排空已接受命令并等待确认；失败或超时显示未完成记录和可操作选择。强制退出不保证未确认事件持久化，必须如实说明；已经确认的记录须能重启读取。

### 8.3 旧 JSON 导入与回退

在启用新写入前，用单个事务导入所有有效旧记录并写完成标记；解析失败、字段不合法或已有目标记录内容冲突时不覆盖来源，也不把导入失败当空账本。重复导入不重复计数。同 ID 相同记录可核对后复用，不同记录应明确冲突。

完成标记提交后再归档来源；归档失败只提示，后续按标记恢复，不能重复导入。不得覆盖既有归档文件。新旧存储不双写；完成迁移后 SQLite 是唯一真相。

新库产生记录后，不能直接运行只读旧 JSON 的旧二进制并宣称回滚成功。回退前必须停写，导出完整新库到经校验的旧格式快照，保留新库备份，再切换；尚未实现该导出时明确不支持旧版本数据回退，不能使用过期 JSON 覆盖新记录。

## 9. 清理意图与编辑器生命周期

### 9.1 清理队列

`StoreCleanups::load` 区分 missing、正常载入、损坏、I/O 失败。missing 才可得到空表；其余错误保留原文件、在设置应用页展示清理记录不可用，并禁用会覆盖不可读台账的持久化修改。应用其他功能可以继续，但不能报告“已清完”或“无待办”。

成功载入的意图写入失败时保留内存任务和 dirty 状态，向 UI 暴露重试；重复 request 即使条目已存在，也必须能重试此前失败的持久化。finish / fail 同样传播失败，避免只更新内存后静默退出。JSON 原子写使用同目录唯一临时文件和文件同步；失败保留旧版本并清理本次临时文件。不得把此保证扩大为任意硬件断电必不丢数据。

数据清理继续在真实卸载成功且 webview 离池后执行；失败或不支持的清理保留可见状态。损坏台账的恢复需从有效备份或可核实的意图恢复，不按目录猜测后执行广泛删除。

### 9.2 创建与重试

将 live / ready / error 的组合改为明确的 `Idle / Building / Ready / Failed / Closed` 创建状态，可见性与几何独立保存。失败后再次打开或点击重试可创建新 generation，清理旧句柄和错误；旧 generation 的 Built / Page 回包不得改变新实例。

隐藏 Ready 面板保留文档与撤销栈；显示不等于重建。创建失败的重试、同步故障恢复、主动关闭是不同操作。重试不能绕过同步层的草稿保护；主窗口退出继续销毁所有相关句柄。提示文案必须与真实可执行动作一致。

## 10. 组合根与 CI

按职责把 product 的面板消息路由、订阅构造、原生视图同步和启动接线拆成子模块，组合根保留状态所有权与装配。具体文件名按编译依赖确定，不以行数为唯一目标，不创建通用动态消息总线或第二份面板状态。不在移动代码的同一变更中改写业务语义。

CI 分层：

- PR：格式、全 targets 编译、核心 Rust 行为测试、无窗口 TypeScript 同步测试、fixture 与嵌入 bundle 一致性、原有依赖门禁。
- 定时 / 手动：完整种子属性测试、Release 性能基准。快速集必须仍覆盖关键块身份与并发不变量，不能把所有属性验证移走。
- 有图形和进程查询能力的 macOS：生产 webview harness、生命周期、输入法 / 撤销与宿主回收。缺失能力明确标记未验证，不能用忽略断言冒充通过。

新增同步测试使用项目既有 TypeScript 编译工具与 Node 测试运行器，测试纯同步状态，避免为此引入浏览器自动化依赖。Rust / TS 协议契约用共享 JSON fixture 验证，TypeScript 使用判别联合类型并校验入站数据。web 源码改变必须重建并提交 `dist/cm.html`。

发行验证采用隔离 checkout 和干净 Cargo 配置，确认没有个人路径 patch。保留用户配置和现有未提交改动；若需要共享库变更，先另行记录所有权和统一 pin 方案，不把本地联调结果当成发布依赖可构建的证据。

## 12. 交付与风险管理

恢复性、协议 / 性能、账本迁移、纯结构拆分分别形成可审阅变更。协议升级必须让 Rust 与嵌入页面同时落地，不能单边发布。数据迁移不能用删除用户文件或恢复旧快照掩盖失败。收益不足时保留测量和正确性修复，记录未达标项，不能把性能阶段标记完成。
